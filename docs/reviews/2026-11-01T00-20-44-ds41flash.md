# Drizziq 1.4.1 code review

- **Repository:** `/home/psyke/Projects/drizziq`
- **Reviewed commit:** `1abcf79` (`Release Drizziq 1.4.1`), branch `main`
- **Review time:** 2026-11-01 00:20 CET / 2026-10-31 23:20 UTC
- **Scope:** all 30 production Kotlin files, 13 JVM test files, `PhoneExercise`, Python verification tooling, Gradle configuration, manifest/resources, bundled metadata, notices and documentation.
- **Mode:** read-only review. No source or test changes were made.

## Summary

No normal-path production crash or data-exfiltration defect was found. The main risks are verification integrity and a small number of data/persistence edge cases:

- Four instrumentation checks are broken or false-green, so the device suite is less trustworthy than its PASS output suggests.
- The full offline integration check expects an `OFFLINE` label that the current UI does not render on Today.
- Daily rain/sunshine completeness is wrong for local days whose midnight is skipped or ambiguous during a DST transition.
- Time-zone validation mixes `java.util.TimeZone` and `java.time.ZoneId`, so an accepted zone can wedge the selected-place forecast.
- Cache and persistence failures are on critical paths in several places.

The JVM suite, Python tooling tests, lint and icon generation are green; see [Verification](#verification).

## High-severity findings

### H-1. Unknown instrumentation phase reports PASS

**Location:** `app/src/androidTest/java/app/drizziq/PhoneExercise.kt:230-1833`

The `when (phase)` dispatch has no `else`, and after the dispatch every path reaches:

```kotlin
result.putString("result", "PASS")
finish(0, result)
```

Any typo in `tools/verify_phone.py`, any removed phase, or any new phase not yet registered is therefore reported as a successful test run.

**Evidence:** running an unregistered phase on the connected device returns PASS:

```text
adb -s 97be12c5 shell am instrument -w -e phase review-unknown \
  app.drizziq.test/app.drizziq.PhoneExercise
INSTRUMENTATION_RESULT: result=PASS
```

This is already noted as an open item in `docs/future/TESTING.md:30-34`; it is still present.

**Impact:** regression checks can disappear without the gate failing. This is the highest-value test defect in the report.

**Recommendation:** add an explicit `else -> error("Unknown phase: $phase")`, preferably backed by a phase registry that also drives the runner, and a runner test that asserts an unknown phase fails.

### H-2. `forecast-status` phase deterministically fails

**Location:** `PhoneExercise.kt:781-793`, against `MainActivity.kt:428` and `MainActivity.kt:719-721`.

The check assumes the first child of the forecast content body is a `ViewGroup`:

```kotlin
bannerAbsent = body().getChildAt(0) is android.view.ViewGroup
```

On Today, `buildHourly()` inserts the date heading first, and that heading is a `TextView`. The assertion therefore fails even when no refresh banner was inserted.

**Evidence:** focused run on `97be12c5`:

```text
java.lang.IllegalStateException: Status banner inserted above Today content during refresh
  at app.drizziq.PhoneExercise.onStart(PhoneExercise.kt:791)
INSTRUMENTATION_RESULT: result=FAIL
```

**Impact:** the only check guarding against an inserted refresh banner is unusable. It is also absent from `tools/verify_phone.py`, so it has silently rotted.

**Recommendation:** identify the expected first child by a stable tag (for example tag the Today date heading `today-date` and the first Week row `week-row:0`) instead of by view class. Add the phase to the runner or explicitly classify it as diagnostic.

### H-3. `copy-cleanup` phase selects the hidden forecast scroll view and fails

**Location:** `PhoneExercise.kt:850-862`, with the first visible `ScrollView` lookup at lines 853-857.

After clicking Places, the test filters all `ScrollView`s by `visibility == VISIBLE` and takes the first. `forecastContainer` is gone, but its child `forecastScroll` still has `visibility == VISIBLE`; it is earlier in the hierarchy than `placesScroll`. The test therefore inspects the hidden forecast body, whose first child is the Today date `TextView`, and fails:

```text
java.lang.IllegalStateException: Places must start directly with the buttons
  at app.drizziq.PhoneExercise.onStart(PhoneExercise.kt:862)
INSTRUMENTATION_RESULT: result=FAIL
```

**Impact:** another dead regression check, also absent from the runner. The Places layout itself is probably correct; the assertion is not observing it.

**Recommendation:** use `isShown`/`isVisibleToUser` or find the Places scroll view by a stable tag; add the phase to the runner.

### H-4. Full offline integration expects a label that the UI does not render

**Location:** `PhoneExercise.kt:1811-1814`; `tools/verify_phone.py:46-51`; production labels at `MainActivity.kt:604-617` and `ForecastDetailsCard.kt:34-37`.

The offline phase waits for:

```kotlin
has("OFFLINE") && has("STALE") && has("Temperature ")
```

and the full runner additionally requires `"OFFLINE"` in the UI dump. The current UI renders `STALE` in the header/details and `"Offline radar"` only in the Radar notice. There is no uppercase `OFFLINE` label on Today. `has()` is case-sensitive. With cached forecast data, the forecast-details message is not shown either.

**Impact:** a full integration run will fail at the offline phase on an otherwise correct device; it also makes the released offline behaviour look untested.

**Recommendation:** choose one contract. Either add a visible offline label to the forecast/header state and update the tests to assert it, or change both `PhoneExercise` and `verify_phone.py` to assert `STALE` plus the retained-data message (and click Radar for the offline notice). Update `docs/DEVELOPMENT.md` and release-check documentation at the same time.

### H-5. Daily totals are falsely incomplete on some DST transition days

**Location:** `app/src/main/java/app/drizziq/Weather.kt:190-204`

`Forecast.days()` builds the local day boundary with `Calendar`:

```kotlin
val start = Calendar.getInstance(TimeZone.getTimeZone(zone)).apply {
    timeInMillis = h.first().time - 1
    set(Calendar.HOUR_OF_DAY, 0)
    ...
}
val end = (start.clone() as Calendar).apply {
    add(Calendar.DAY_OF_MONTH, 1)
}.timeInMillis
```

This assumes every local day starts at a resolvable `00:00` and that adding one calendar day is the same as the next local start-of-day.

On spring-forward days where midnight is skipped (`America/Santiago` 2026-09-06, `Africa/Cairo` 2026-04-24, `Asia/Beirut` 2026-03-29, `Atlantic/Azores` 2026-03-29, `America/Havana` 2026-03-08), `set(HOUR_OF_DAY, 0)` resolves to 01:00, and `add(DAY_OF_MONTH, 1)` produces 01:00 the next day rather than the next 00:00. The day is 23 hours long, but `end - start` is 24 hours, so `h.last().time == end` is false. On fall-back days where the transition happens at 01:00 (`America/Havana` 2026-11-01, `Atlantic/Azores` 2026-10-25), the ambiguous 00:00 can resolve to the second occurrence, so `h.first().time == startMillis + 3600000` is false.

A JDK 21 replica of the exact `Calendar` sequence reproduced the spring case: for `America/Santiago` 2026-09-06 it produced `start = 2026-09-06T04:00Z`, `end = 2026-09-07T04:00Z`, while the next local start is `2026-09-07T03:00Z` (23-hour day).

**Impact:** `Day.total()` returns `null`, so Week shows `—` for rain and sunshine on affected days, contradicting the documented “completeness respects 23/25-hour daylight-saving transitions” in `docs/DATA.md`. The existing 25-hour Berlin test does not cover midnight/01:00 transitions.

**Recommendation:** derive boundaries from `Instant` + `ZoneId`:

```kotlin
val date = Instant.ofEpochMilli(h.first().time - 1).atZone(ZoneId.of(zone)).toLocalDate()
val startMillis = date.atStartOfDay(ZoneId.of(zone)).toInstant().toEpochMilli()
val end = date.plusDays(1).atStartOfDay(ZoneId.of(zone)).toInstant().toEpochMilli()
```

Add 23-hour and 25-hour tests for `America/Santiago`/`America/Havana` in addition to Berlin.

## Medium-severity findings

### M-1. Time-zone validation accepts IDs that `ZoneId` rejects

**Locations:** `Geocoding.kt:45,72-79`; `MainActivity.kt:884-889`; `ForecastLookup.kt:52-58`; `ForecastPresentation.kt:12`; `SolarCalculator.kt:19`; `Weather.kt:96-101`.

`Geocoding.zone()` and the zone prompt validate against `TimeZone.getAvailableIDs()`, but the forecast, hourly and solar code use `ZoneId.of(place.zone)`. These sets are not identical. On the JDK 21 runtime used for review, 28 of 632 `TimeZone` IDs are rejected by `ZoneId.of()`; examples include `PST`, `CST`, `AST`, `IST`, and `US/Pacific-New`. `TimeZone.getTimeZone("PST")` works, while `ZoneId.of("PST")` throws `ZoneRulesException`.

`ForecastLookup.load()` calls `ZoneId.of(place.zone)` outside its `try` block. If the selected place has one of these IDs, the worker throws before publishing any reading. `Repository.forecast.refreshing` remains true, so `refreshForecast()` returns early forever and the UI remains on “Locating nearest DWD station”. `SolarCalculator` catches the same failure and only shows “Sun times unavailable”. `Times.format()` silently falls back to GMT through `TimeZone.getTimeZone`.

**Impact:** a user can enter an accepted alias in the zone prompt and permanently wedge the selected place until they choose another one; a corrupted/legacy saved zone has the same effect.

**Recommendation:** use one API everywhere. Validate/load with `ZoneId.getAvailableZoneIds()` or `ZoneId.of(value)`; store canonical zone IDs; make `Times` use `ZoneId`; validate persisted zones in `PlaceStore.selected()`/`favourites()`; catch invalid zones in `ForecastLookup` and publish an explicit error. Add tests for `PST` and a midnight-transition zone.

### M-2. Deleting a favourite can crash on a failed preferences commit

**Locations:** `MainActivity.kt:795-807`; `PlaceStore.kt:48-53,70-76`.

`FavouriteCard`'s delete callback calls `store.delete(place)` without a `try/catch`. `delete` → `write` → `commit`; `commit` throws `IllegalStateException` when `SharedPreferences.commit()` returns false. Unlike `choose()` and `saveFavourite()`, this path does not catch the failure, so the exception escapes the main-looper click handler and kills the process.

**Impact:** storage-full/read-only preferences cause a crash instead of a retry message. The same failure path is already tested for `select`, but not for `delete`.

**Recommendation:** wrap the delete call in the same `Toast` handling as saving, keep the list unchanged on failure, and add a `PlaceStore`/UI test using `Memory.failNext`.

### M-3. Cache-write failure discards a successful forecast download

**Locations:** `Repository.kt:167-177,196-205`; `ForecastLookup.kt:107-109`.

`fetch()` parses and validates the downloaded KMZ, then calls `atomic(...)` before returning. If the cache directory is full, read-only, or the rename fails, `atomic` throws; `ForecastLookup` catches the exception and publishes `retained.failed("Refresh failed · connection or data error")`. The successfully downloaded forecast is never displayed. In the `earlier()` path, the same `atomic` failure is swallowed by `withHistory()`'s `runCatching`, so the downloaded historical KMZ is silently dropped.

**Impact:** a cache failure is reported as a network/data failure, and valid DWD data is lost; the user sees stale/error state despite a successful response.

**Recommendation:** make cache writes best-effort (`runCatching { atomic(...) }`) while still returning the parsed result; report a separate cache-warning only if useful. Add a test with a failing cache writer.

### M-4. Radar tile and forecast disk caches are unbounded

**Locations:** `RadarMap.kt:28-33,281-320`; `Repository.kt:154-165,196-213`.

`RadarMap` keeps a 64-entry `LruCache` in memory but writes every requested tile to `context.cacheDir/tiles` and never deletes obsolete files. The `failed` map is also unbounded and retains every failed tile key. Forecast KMZs are cached per station in `filesDir/data` and never pruned; only historical `MOSMIX_L_*` files older than three days are removed, and only after a new historical write succeeds. Tiles are refreshed after seven days but old files are not removed.

**Impact:** storage and memory grow with every viewed map area and searched station; long-lived installs can accumulate large caches. The README/DATA claim that the basemap “caches only tiles viewed” remains true but omits the lack of a bound.

**Recommendation:** add size/age limits and pruning for the tile directory and failed map; prune forecast caches by station/age; remove stale `.part` files. Add a cache-policy test or a testable cache-manager seam.

### M-5. Cached radar PNGs are never validated or regenerated

**Locations:** `Repository.kt:345-363`; cache loader at `Repository.kt:283-284`; palette `RadarData.kt:70-90`.

The radar decoder writes a PNG only when `dest.exists()` is false. The cache loader only checks that the path exists. There is no cache version, palette version, checksum, or decode validation. If a PNG is truncated/corrupt, or if the app’s palette/projection code changes, the old image is reused indefinitely. `MainActivity` shows “Radar frame unavailable” when `BitmapFactory` returns null, but the file remains and will keep being reused.

**Impact:** a corrupt frame or an app update with changed radar colours can permanently show stale/wrong pixels; a refresh cannot repair the frame.

**Recommendation:** validate the cached image (decode dimensions/checksum), store a cache/palette version in `radar.json`, regenerate on mismatch/corruption, and delete bad files on decode failure. Add a corrupt-PNG test.

### M-6. Fixed `.part` cache path can race between workers

**Locations:** `Repository.kt:102,134-138,220-255`.

`Repository` owns two workers and `select()` can be called again while a previous load is still running (for example two quick favourite taps / a refresh while a place selection is in flight; `refreshForecast()` only guards the current reading’s `refreshing` flag). `atomic()` always writes `file.path + ".part"`:

```kotlin
val temp = File(file.path + ".part")
temp.writeBytes(bytes)
check(temp.renameTo(file))
```

Two writes for the same station can interleave in the same `.part` file; one can rename a partially overwritten file, after which the cache may be corrupted and a later refresh reports a cache/parse failure.

**Impact:** rare but user-visible cache corruption/refresh failure under overlapping selections.

**Recommendation:** use a unique temp file (`File.createTempFile` or a random suffix) and atomically rename, or serialize cache writes per target. Consider cancelling/deduplicating the previous fetch for the same station.

### M-7. Numeric formatting mixes locale-dependent and `Locale.US` separators

**Locations:** `MainActivity.kt:1010-1013` (`Locale.US`); `CurrentWeatherHeader.kt:78-80,105-108`; `ForecastDetailsCard.kt:49-54,85-95,101-106`; resources `values/weather_header.xml:3-7`, `values/forecast_details.xml:2-11`.

The hourly/Week/coordinates code formats with `Locale.US` (dot), while the header temperature and forecast details use `Context.getString(...)` and therefore the device locale. The checked-in screenshot shows the inconsistency directly: the header displays `5,7°` on a German device while coordinates display `48.1381°N`. Forecast details also render locale-dependent latitude/longitude/distance.

**Impact:** the HUD mixes decimal separators; values copied or compared between sections can look inconsistent. The app’s UI text is English, so a fixed HUD locale is likely intended.

**Recommendation:** choose one policy. For a fixed HUD, use `Locale.US`/`Locale.ROOT` for all formatted numbers (including `getString` resources that embed numbers), or make every numeric surface locale-aware. Add a test with a German default locale.

### M-8. One malformed favourite hides the whole list

**Location:** `PlaceStore.kt:60-64`.

`favourites()` maps every array entry inside one `runCatching` and returns `emptyList()` if any entry fails. A single corrupt/legacy row therefore hides every valid favourite. There is also no upper bound.

**Impact:** a partial data issue becomes a total loss of the visible favourite list; the data may still exist but cannot be recovered through the UI.

**Recommendation:** parse entries independently, skip/log malformed entries, migrate valid ones, and optionally cap the list. Add tests with one corrupt entry among valid entries.

## Low-severity findings

- **L-1. Unbounded KMZ/XML input.** `Weather.kt:273-280` inflates a ZIP entry without a decompressed-byte limit, and `Weather.kt:313-314` appends every text node to an unbounded `StringBuilder`. The HTTP limit applies only to compressed bytes. A malicious/compromised DWD response can cause OOM/ANR; `ForecastLookup` catches `Exception`, not `Error`, so an OOM can leave `refreshing` stuck. Add a counting decompressed stream, text-node limit, entry limit, and `disallow-doctype-decl`/entity hardening.
- **L-2. API 24/25 header clipping.** `CurrentWeatherHeader.kt:11-24` enables auto-size only on API 26+. The temperature column is about 116 dp wide (180 dp header minus 60 dp condition and margin); a 42 sp negative/large value such as `-40.0°` can clip on API 24/25. Provide a support-library auto-size fallback, smaller default, or ellipsize; add a minimum-API layout check.
- **L-3. Notices dialog lifecycle.** `MainActivity.kt:823-835` shows the Data & licences `AlertDialog` without tracking it in `PlaceChoices` or dismissing it in `onDestroy`. A rotation/finish while it is open can leak a window. Track it like the search/favourite dialogs or dismiss it in `onStop`/`onDestroy`.
- **L-4. Network callback while stopped.** `MainActivity.kt:101-121` checks `ready` and `dead`, but not `active`; `onStop` at lines 950-956 does not unregister the callback. A connectivity change while backgrounded can call `repo.connection()` and `refresh()`, starting downloads. Register in `onStart`/`onStop` or guard with `active`.
- **L-5. Weather-code icon gaps.** `WeatherIcons.kt:14-56` maps labels for codes 4-44/46/47/87-94 but returns `weather-unknown` for many of them; `weatherLabel()` has categories for those codes. `artwork/icons/README.md` says every MOSMIX `ww` code is mapped. Add icons or explicitly document the supported subset and test the fallback.
- **L-6. Partial radar projection validation.** `RadarData.kt:113-122` checks `+proj`, `+lat_ts`, `+lon_0`, `+a`, and `+x_0`, but not `+y_0`, `+b`/ellipsoid, `+lat_0`, or units. A DWD projection change could pass validation and be projected with the hard-coded DE1200 constants. Validate the full PROJ parameter set or parse the parameters.
- **L-7. Old radar frame survives decode failure.** `MainActivity.kt:675-686` sets `frameError` when `BitmapFactory` returns null but does not clear `map`'s previous frame. The timeline/accessibility can describe the new frame while the map still shows the old one. Call a clear/reset path before leaving a failed frame.
- **L-8. Hourly accessibility gaps.** `HourlyForecast.kt:135-150` always announces `Rain — millimetres...` for missing precipitation; `HourlyForecast.kt:205-208` gives humidity cells no content description/unit. Add “unavailable” strings and humidity descriptions analogous to gust/probability.
- **L-9. Search status colour.** `PlaceChoices.kt:210-213` and `:273-280` reset the status text without resetting its colour; after an amber error/failure, the hint/empty state can remain amber. Set `Hud.muted` in those branches.
- **L-10. Dead code.** `MainActivity.section()` (`MainActivity.kt:313-317`) and `RadarMap.reset()` (`RadarMap.kt:224-231`) have no callers after the header/layout refactors. Remove them or restore their intended use.

## Test coverage and tooling gaps

- **Unregistered phases.** `PhoneExercise` contains focused phases that the default and full runners never execute: `lint-resources`, `svg-icons`, `hourly-refresh`, `day-forecast`, `header-weather`, `forecast-status`, `copy-cleanup`, `recenter-probe`, `geocoding-probe`, `station-benchmark`, and `radar-gestures`. `docs/future/TESTING.md:30-34` acknowledges this. `header-weather`, `day-forecast`, and `hourly-refresh` passed when run individually; `forecast-status` and `copy-cleanup` failed (H-2/H-3).
- **Full-run restoration.** `verify_phone.py --full` runs `main`/`persistence`, which create/delete favourites and change the selected place and camera, but does not restore them. `--places-integration` restores its own snapshot, but when it is run after the default smoke phases, it snapshots the camera already changed by `viewport-save`, not the user’s pre-run camera. Document this explicitly or add a top-level snapshot/restore.
- **Missing deterministic tests.** There are no JVM tests for midnight/01:00 DST zones, `TimeZone` aliases vs `ZoneId`, favourite-delete failure, cache-write failure, cache eviction/validation, overlapping cache writes, mixed numeric locales, or oversized KMZ/XML. These correspond to the medium/high findings above.
- **Live-service device dependency.** The default and full suites still depend on live DWD/Open-Meteo/OSM responses. The existing `docs/future/TESTING.md` plan is the right direction; it is not implemented.
- **`PhoneExercise` size.** A single 1,840-line instrumentation class mixes runner dispatch, UI helpers, diagnostics and live integration. The phase registry and a stable view-tag helper would reduce the class of bit-rot represented by H-2/H-3.

## Documentation and compliance observations

- **README prerequisites.** `README.md:31` lists only JDK 21, Android SDK 37 and Build Tools 36.0.0, but `app/build.gradle.kts:49` runs `python3 tools/generate_icons.py` from `preBuild`, and the tooling tests require Python 3.11+. Add Python 3 to the build prerequisites.
- **ODbL source offer.** `docs/DATA.md:51` and `app/src/main/assets/notices.txt:9` say the timezone database source is distributed in `https://codeberg.org/k4r/drizziq`; the README badge describes that repository as private. If a public APK is distributed, an ODbL source offer pointing at a private repository may not satisfy the licence. Publish the database source separately or make the repository/source offer public.
- **Stale planning doc.** `docs/future/TESTING.md:3` says it targets the Drizziq 1.3.0 tree, while the reviewed tree is 1.4.1. Update the baseline or mark the document archival. It also correctly flags the false-PASS runner and unregistered phases, which remain open.
- **Build-only wrapper licence.** `gradle/wrapper/gradle-wrapper.jar` is tracked but has no separate Gradle/Apache notice. This is build-only and not packaged in the APK, so it is a low-priority repository-compliance cleanup.
- **Metadata headers.** `timezones.tree` and `timezones.txt` carry no ODbL/CC0 provenance header; the licence and provenance are documented in `docs/DATA.md`, `notices.txt` and `docs/licenses`. Keep as a known low-priority documentation gap.
- **OSM requests.** Tile requests do not send `If-None-Match`/`If-Modified-Since`; the seven-day refresh always downloads the full tile. This is not a correctness bug, but conditional requests would reduce bandwidth and align better with the tile service’s caching guidance.
