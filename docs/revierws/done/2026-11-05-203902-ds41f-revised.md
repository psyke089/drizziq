## Assessment

The original report identifies several real issues, but overstates some consequences and mixes defects, design choices, optional improvements and test suggestions under one severity scale. No finding reviewed here establishes a high-severity defect. That does not establish the absence of other defects, secrets, data-loss paths or licence problems across the repository.

The strongest actionable findings are unnecessary queued radar decodes (R3), misleading empty-offline messages (R5), and replacement of an equally recent in-memory forecast with a cached reading during refresh (R8). Repeated forecast downloads (R1) are a credible efficiency concern. Radar cache rejection is deliberately conservative and tested; partial salvage would be a policy improvement rather than restoration of an existing guarantee (R6).

Week's omission of earlier-issue hours (R4) and keyboard Search's inability to bypass cache (R2) are confirmed behaviors, but their desired product behavior needs to be distinguished from the original report's unsupported failure scenarios.

## Findings and recommendations

### R1 — Automatic refresh repeatedly requests both products

**Evidence:** [MainActivity.kt](../../../app/src/main/java/app/drizziq/MainActivity.kt), lines 137–144 and 935–940; [Repository.kt](../../../app/src/main/java/app/drizziq/Repository.kt), lines 278–291 and 372–375; [ForecastLookup.kt](../../../app/src/main/java/app/drizziq/ForecastLookup.kt), lines 101–103.

While the Activity is active and the repository believes it is online, a 30-second tick calls `refresh()` when more than 300,000 ms have elapsed since `lastRefresh`. This is approximately a five-minute cadence, not an exact five-minute schedule. `refresh()` requests both forecast and radar regardless of the selected page. Busy guards can skip overlapping work. Selecting a place also starts radar cache loading/refresh when radar data is absent, before the radar page is opened.

The forecast path reparses available cache data and performs an unconditional latest-KMZ fetch. Radar uses a conditional request and can reuse cached frames. Repeated forecast transfer/parsing is avoidable; the magnitude of traffic and battery cost was not measured. A five-minute radar refresh may be intentional for a five-minute product, and keeping hidden radar warm may be an acceptable hobby-app tradeoff.

**Recommendation:** First reduce repeated forecast work with a modest successful-fetch interval or conditional HTTP validation. Keep explicit manual refresh and connectivity recovery useful. If page-based radar gating is adopted, refresh when entering Radar as needed; changing only the tick would leave initial hidden-page loading intact.

The nine-hour forecast freshness threshold is a stale-data indicator, not a required polling interval. Waiting until an issue is stale can delay receipt of a newer available issue. No new refresh abstraction or scheduler is necessary unless the chosen policy warrants it.

### R2 — Keyboard Search resubmits but cannot bypass warm results

**Evidence:** [PlaceChoices.kt](../../../app/src/main/java/app/drizziq/PlaceChoices.kt), lines 159–185 and 258–266; [SearchDebounce.kt](../../../app/src/main/java/app/drizziq/SearchDebounce.kt), lines 33–37; [Geocoding.kt](../../../app/src/main/java/app/drizziq/Geocoding.kt), lines 212–239; [geocoding.xml](../../../app/src/main/res/values/geocoding.xml).

Both typing and IME Search reach the same submission function, which passes `refresh = false`. A warm cache therefore returns immediately without transport. The hint says keyboard Search can retry, but the UI has no explicit way to refresh successful cached results apart from clearing the cache or waiting for expiry.

The original scenario—warm results, then a forced network failure from this dialog, followed by the same failure on every keyboard retry—is not supported by the UI callers. No caller here requests `refresh = true`. On a warm-cache submission, the UI sets the normal cached-results message, rather than preserving the previous failure. With no cached result, keyboard Search does retry the transport, subject to connectivity and Retry-After.

**Recommendation:** Treat this as a small cache/interaction decision. If IME Search should request new results, propagate a force flag while still honoring offline state and Retry-After. Otherwise clarify that cached results are reused. Existing `GeocodingTest` already tests forced refresh and failure retention; any added regression should cover the missing UI-to-policy wiring, not duplicate that policy test.

### R3 — Timeline input can build a queue of obsolete bitmap decodes

**Evidence:** The timeline is implemented in [RadarMap.kt](../../../app/src/main/java/app/drizziq/RadarMap.kt), lines 462–470, not a separate `RadarTimeline.kt` file. [MainActivity.kt](../../../app/src/main/java/app/drizziq/MainActivity.kt), lines 825–875, handles frame requests.

Down, move and up events select the nearest frame on every event, including repeated selection of the same index. For each uncached request, `requestFrame` increments a token and queues `BitmapFactory.decodeFile` on a single-thread executor. It does not deduplicate an in-flight filename or check the token before decoding. The main-thread completion discards obsolete images only after disk read/decode has occurred.

Consequently, input can queue redundant full-frame decodes and delay the final selection. The three-entry bitmap cache helps frames already decoded and accepted; it does not coalesce pending work. Actual jank and queue size were not measured on a phone.

**Recommendation:** Deduplicate the pending filename and skip obsolete queued work before decoding, or use one replaceable pending request. Preserve the last successfully displayed image and the single playback loop. A minimal change is preferable to a new rendering framework. Verify rapid scrubbing on the usual phone; a deterministic queue-policy test is useful if a small pure policy is introduced for this behavior. Avoid tests tied to touch-event counts or incidental view structure.

### R4 — Week aggregates use only the latest issue's hours

**Evidence:** [Weather.kt](../../../app/src/main/java/app/drizziq/Weather.kt), lines 185–225; [ForecastPresentation.kt](../../../app/src/main/java/app/drizziq/ForecastPresentation.kt), lines 11–29; [ForecastLookup.kt](../../../app/src/main/java/app/drizziq/ForecastLookup.kt), lines 63–75 and 114–117.

Today merges `earlier + hours`, with latest-issue values winning duplicate timestamps. `Forecast.days()` groups only `hours`. Thus a day that is complete across the combined inputs can remain incomplete for Week, and rain/sun totals remain unknown there. The difference also affects which hours contribute to daily high/low, maximum wind and condition.

This is a real presentation-policy difference. It is not proof that the fixture currently has a complete combined day: that also requires successful historical loading, every required interval, and nonmissing rain/sun fields. The historical lookup selects an issue intended to cover local midnight; it need not be the immediately preceding issue relative to the latest issue.

`AGENTS.md` explicitly requires historical hours for Today and complete days for Week, but does not expressly say Week must merge issues. The current unknown totals preserve the no-partial-total rule. The original assertion that this generally affects the following day is not established.

**Recommendation:** Decide whether Week should describe complete combined forecasts or latest-issue-only forecasts. If combined, merge and sort with latest values winning before aggregation, retain complete-local-day and missing-field checks, and describe earlier values as forecasts. Add a focused test with explicitly complete earlier/latest inputs, plus overlap and missing-interval cases. Preserve independent civil-date boundaries for DST. If latest-only is intentional, document that distinction.

### R5 — Empty offline states claim that data was retained

**Evidence:** [Repository.kt](../../../app/src/main/java/app/drizziq/Repository.kt), lines 256–261; [ForecastLookup.kt](../../../app/src/main/java/app/drizziq/ForecastLookup.kt), lines 97–99; [ReadingPolicy.kt](../../../app/src/main/java/app/drizziq/ReadingPolicy.kt), `Reading.failed`.

The offline paths choose retained-data wording regardless of whether the payload exists. `failed()` correctly makes a null-data reading `ERROR`, so there is no invented forecast or freshness error here. The problem is contradictory copy alongside the empty forecast state. Radar stores similar wording, although its main notice can mask it.

**Recommendation:** Choose messages based on payload presence, for example “Offline · no saved forecast” versus “Offline · showing saved forecast.” Add one pure empty-offline forecast regression when implementing the change. Existing retention tests cover payload preservation, not this wording distinction; a new phone phase is not required solely for copy.

### R6 — A bad cached frame rejects the snapshot; invalid-file hints are unused

**Evidence:** [RadarCache.kt](../../../app/src/main/java/app/drizziq/RadarCache.kt), lines 140–203; [Repository.kt](../../../app/src/main/java/app/drizziq/Repository.kt), lines 385 and 419; [RadarCacheTest.kt](../../../app/src/test/java/app/drizziq/RadarCacheTest.kt).

`RadarCache.read()` deliberately returns a sequence only if all referenced frames pass validation. A missing, truncated or wrong-sized frame rejects the snapshot, and repository callers ignore `invalid`. For a PNG failure, parsing stops at the first failure; the list is not an inventory of every bad file. Version/palette mismatches instead return the safe referenced filenames.

This means valid neighboring files cannot contribute to startup playback or refresh reuse through that rejected snapshot. Online, a refresh without a snapshot must fetch the latest archive and attempt history again. Offline, cached radar is unavailable even when some files are valid. An already displayed in-memory sequence is not automatically cleared by this read failure.

Whole-snapshot rejection is explicitly documented and tested. It should not be described as a violation of a partial-retention contract. Nor does an undeleted bad file necessarily prevent repair: successful decoding atomically overwrites the same destination filename. Deleting it first does not restore valid-frame reuse or solve a persistent decoder failure.

**Recommendation:** Either retain the simple conservative contract and remove/clarify the unused cleanup hint, or deliberately add partial reuse if failures on real devices justify it. For partial reuse, represent history gaps honestly, keep observed/forecast requirements appropriate to each stage, and attach HTTP validators only when a 304 can be fulfilled safely from retained frames. Do not blindly turn a damaged snapshot into a conditional request that can repeatedly accept 304 without the missing latest frames. Preserve valid files during attempted repair.

### R7 — Tile workers can race with later connectivity updates

**Evidence:** [RadarMap.kt](../../../app/src/main/java/app/drizziq/RadarMap.kt), lines 88 and 303–317; [MainActivity.kt](../../../app/src/main/java/app/drizziq/MainActivity.kt), line 793.

`online` is a plain mutable property written on the main thread and read inside a tile worker. Executor submission publishes writes made before that submission, so the original blanket statement that there is no happens-before edge is incorrect. A later connectivity update, after submission, is not ordered with the worker's read of this property.

**Recommendation:** Use `@Volatile` if workers should consult the latest flag, or capture an immutable request-time value if that is the intended policy. Neither option guarantees that a network remains available throughout a request. No stale read was observed in this review; this is a small concurrency correction, not a demonstrated outage or privacy breach.

### R8 — Equal-issue disk cache can replace a LIVE in-memory reading

**Evidence:** [ForecastLookup.kt](../../../app/src/main/java/app/drizziq/ForecastLookup.kt), lines 77–94; [Repository.kt](../../../app/src/main/java/app/drizziq/Repository.kt), lines 332–346.

A same-place refresh retains the previous reading, but accepts disk cache whose issue is equal to it and emits `CACHED` online. This can briefly downgrade LIVE state. If the in-memory successful-download time is newer than the disk receipt, the displayed receipt can also move backward. The timestamps need not differ on every refresh.

**Recommendation:** Avoid replacing an equally recent retained payload just to announce cached state; retain its successful-download timestamp and indicate refreshing separately. Add a focused equal-issue LIVE/cache regression. Changing `>=` to `>` would avoid that equal-issue emission, but would not avoid reparsing: `source.cached()` has already been called before the comparison. Treat any disk-read optimization separately.

### R9 — Upfront PNG validation is a possible optimization, not a lazy-decode violation

**Evidence:** [RadarCache.kt](../../../app/src/main/java/app/drizziq/RadarCache.kt), lines 25–78 and 177–180; [MainActivity.kt](../../../app/src/main/java/app/drizziq/MainActivity.kt), lines 850–857.

Cache loading reads each PNG and checks chunk structure/CRCs before publishing the saved sequence. Bitmap decoding still occurs on demand for the selected frame. The implementation therefore follows the project's requirement to avoid decoding the entire saved bitmap sequence before first display.

No startup latency has been measured. The small checked-in PNG is insufficient evidence that production sequences are cheap or expensive. Header-only validation would weaken the existing corruption guarantees, and trusting a manifest-stored checksum without checking current bytes would not detect subsequent file corruption.

**Recommendation:** Keep the current validation unless startup cost is observed on the usual phone. Any later streaming or lazy-validation change should retain bounded inputs, version/palette checks and honest failure handling. Do not trade away cache validation solely on this speculative performance finding.

### R10 — Hourly highlight callbacks follow attachment, not visibility

**Evidence:** [HourlyForecast.kt](../../../app/src/main/java/app/drizziq/HourlyForecast.kt), lines 44–50 and 250–257; [MainActivity.kt](../../../app/src/main/java/app/drizziq/MainActivity.kt), lines 1155–1186.

The minute timer stops on detach, while Activity pause/stop does not explicitly stop it. A hidden but attached hourly view can continue scheduling callbacks and invalidating its track. This can also occur when its parent screen is hidden. There is no wake lock, network operation or measured battery impact associated with this finding.

**Recommendation:** If tidying this lifecycle path, gate callbacks on effective view/window visibility or existing Activity lifecycle state, and restart without duplicate callbacks. A broader timer architecture is unnecessary.

### R11 — “Current” uses nearest-hour semantics

**Evidence:** [Weather.kt](../../../app/src/main/java/app/drizziq/Weather.kt), lines 204–205; [ForecastPresentation.kt](../../../app/src/main/java/app/drizziq/ForecastPresentation.kt), `currentHourColumn`; [CurrentWeatherHeader.kt](../../../app/src/main/java/app/drizziq/CurrentWeatherHeader.kt), `bind`.

`Forecast.current()` selects the nearest latest-issue hour within an inclusive ±one-hour window. It can select a future timestep, including at an ordinary half-hour boundary when both neighboring hours exist. The Today highlight instead uses the containing column. The header's condition accessibility description includes the selected validity time.

Nearest-hour selection is not inherently incorrect for a forecast summary, and the repository does not require a containing-hour header. Selecting a previous timestep would also need care because instantaneous fields and preceding-hour totals have different meanings. The original recommendation to prefer a prior hour but fall back to the next hour would retain its own example of future selection.

**Recommendation:** Treat this as a product decision. If changing it, define selection, gap and earlier-issue behavior explicitly and test boundaries. No immediate fix is established by this report.

### R12 — Private radar manifests lack some semantic checks

**Evidence:** [RadarCache.kt](../../../app/src/main/java/app/drizziq/RadarCache.kt), lines 156–194 and 244–245; [RadarData.kt](../../../app/src/main/java/app/drizziq/RadarData.kt), lines 103–132; [RadarRefresh.kt](../../../app/src/main/java/app/drizziq/RadarRefresh.kt), lines 81–113 and 155–164.

The reader already validates version/palette, a nonempty frame list, safe filenames, PNG structure/bounds and agreement with declared dimensions. Empty-list and path-traversal rejection have focused tests. The original recommendations to add these checks were redundant, and its suggestion that an accepted empty sequence could crash `renderRadar()` was unsupported.

Missing checks include the validity-time/issue/lead relationship, lead bounds/cadence, finite and positive grid spacing, frame ordering/duplicates, and consistency of historical versus latest-issue entries. A structurally valid but semantically damaged private manifest can therefore distort rendering or timeline behavior. This is private-cache robustness, not a demonstrated remote-input exploit. The current round-trip test helper itself uses a lead-zero frame whose validity is five minutes after issue, so tightening time validation requires correcting that fixture intentionally.

**Recommendation:** Add a small set of semantic checks if this path is hardened. Apply observed/forecast completeness requirements to the appropriate snapshot stage: the refresh pipeline intentionally publishes partial sequences while loading, so a blanket requirement on every `RadarSequence` would be wrong. Keep malformed-cache recovery independent of successful-download timestamps. No broad schema framework is needed.

### R13 — Loading offline radar cache enters a failed-refresh phase

**Evidence:** [Repository.kt](../../../app/src/main/java/app/drizziq/Repository.kt), lines 381–419 and 532–537.

After loading saved radar, the repository calls `refreshRadar()` regardless of connectivity. It publishes DOWNLOAD/refreshing state, then the worker checks `online` and fails before any HTTP request. This can produce checking/receiving/failure progress for a known offline state. Transient states may be too brief to see; their actual visibility was not checked on a phone.

**Recommendation:** When automatic cache loading finishes offline, retain the saved stale sequence and stop with an idle/offline status. Let foreground recovery trigger the existing refresh path. An explicit offline manual refresh may still report unavailability, but should not imply a download occurred.

## Optional maintenance and test guidance

### R14 — Unused paths

`layers.svg` has no identified runtime use beyond its generated icon mapping. `RadarCache.reusable()` is used only by tests. Production HTTP callers do not request a non-null Range, although `Http.bytes` and its reader support one.

These are small cleanup opportunities, not functional bugs. If removed, edit SVG sources and regenerate icons rather than editing generated resources. Preserve tests that exercise useful PNG validation through production entry points. If Range support is retained, clarify its supported bounded-range format before adding callers; lack of general HTTP Range syntax is not a current failure.

### R15 — Favourite save and delete use different identities

`PlaceStore.save` replaces by coordinates; `delete` removes by full value equality. The UI currently passes the stored favourite object, so no failing current user path was established. Exact-value deletion could also intentionally avoid deleting a subsequently replaced entry.

Do not introduce stable IDs or change deletion semantics solely for symmetry. If a real caller needs coordinate-based deletion, define that behavior and add a focused test then.

### R16 — Target tests to adopted behavior changes

Existing tests already cover `CitySearch(refresh = true)`, Retry-After, debounce/IME immediate submission, offline matching-cache retention, earlier-hour merging for Today, DST daily completeness, corrupt/missing/wrong-size radar frames, version/palette rejection, empty manifests and unsafe filenames. The phone exercise includes ordinary scrubbing, decode failure, offline retention and lifecycle paths. These do not prove every scenario above, but “missing tests” should not erase this coverage.

Useful additions alongside actual fixes are the equal-issue forecast-state regression (R8), empty-offline wording (R5), and UI force propagation if adopted (R2). Add combined-source day tests only if that Week policy is chosen (R4), and coalescing/cache-semantic tests with the corresponding implementation changes (R3/R12). No focused JVM `ZoneLookup.at` coordinate test was identified; this remains an optional confidence improvement, not evidence of a lookup defect. Android ownership makes that test less direct than for the existing pure policies.

Follow repository guidance: focused checks while iterating, usual-phone inspection for UI changes, and no new test framework, device matrix or benchmark project without a concrete need.

## Architecture, attribution and build observations

The overall architecture follows the project constraints: platform Views, one Activity, Repository ownership of forecast/radar work, pure policy/parsing helpers, and explicit executor/generation handling. The original architecture diagram was too approximate to serve as a dependency map: `RadarMap` owns tile loading, and Activity-owned solar calculation is separate from place search. Repository callbacks are generation-checked, but that does not imply queued bitmap work is coalesced (R3).

Positive safeguards visible in the reviewed paths include bounded MOSMIX/ODIM inputs, explicit missing values, complete-day totals, source-time preservation, conditional radar/tile requests, atomic cache writes, versioned PNG validation, and separation of issue freshness from successful-download timestamps. Their presence is not a guarantee that every failure path is correct.

Bundled notices identify the data providers and dependency licences. Search credits link Open-Meteo and GeoNames; saved places retain provenance fields, while favourite cards do not display a per-place credit. This observation alone establishes neither compliance nor a breach. The original broad “no licence gap” conclusion, current provider-term assertions and exhaustive no-secrets/no-logging claims exceed the verification performed in this revision. No provider usage or dependency change is proposed here.
